# Every pull request is merged with a merge commit

Pull requests into `dev` and the promotion pull request from `dev` into `main` are
both merged with a **merge commit**. Squash and rebase merges are not used.

Keeping every commit preserves who changed what, one change at a time, instead of
collapsing a feature into a single commit authored by whoever pressed the button.
It is also what release-please needs: it reads the individual commits to build the
changelog and choose the version bump.

## Consequences

Every commit on a feature branch lands on `dev`, then on `main`, and release-please
reads each one. A single non-conventional message is enough to pollute the changelog,
so commit messages are checked twice: locally by a `commit-msg` hook, and in CI by
the `Commitlint` job, which is a required check. The rules are in
[docs/GIT_RULES.md](../GIT_RULES.md).

Merge commits generated by git itself (`Merge branch 'dev' into feature/x`) are
ignored by both the check and release-please. Updating a branch with
`git pull --rebase` still keeps the history easier to read.

A rebase merge is not an acceptable substitute: it rewrites commit SHAs, which
would permanently fork `dev` from `main` and break the back-merge in
[ADR-0003](./0003-automatic-back-merge-from-main-to-dev.md). The rule is enforced by
branch rulesets — see [ADR-0007](./0007-merge-methods-enforced-by-rulesets.md).
